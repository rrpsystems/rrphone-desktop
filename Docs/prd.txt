Visão Geral do Produto 1.1 Objetivo Desenvolver o RRP Softphone, um aplicativo de comunicação VoIP multiplataforma que funciona como ramal corporativo completo para qualquer usuário gerenciado pela RRP Systems, com a possibilidade de habilitar, por plano contratado, o módulo de integração nativa com o sistema de call center. O produto utiliza a liblinphone SDK (Belledonne Communications — GPL v3) como engine SIP/RTP/vídeo, com UI e integrações desenvolvidas do zero para o ecossistema RRP. ⚠ Decisão Arquitetural — SDK Puro, Não Fork do App Demo O RRP Softphone NÃO é um fork do app demo linphone-android/linphone-ios. O app demo da Belledonne tem ~150 telas, código legado (Objective-C/Java) e remoção de funcionalidades pode quebrar o core. A abordagem adotada na v3 é: Android: liblinphone como dependência .aar em projeto Kotlin/Jetpack Compose novo iOS: linphone-sdk como framework Swift Package Manager em projeto SwiftUI novo Desktop: liblinphone como biblioteca Qt/C++ em projeto CMake novo Isso garante APK/IPA enxuto, UI 100% customizada e ciclo de build controlado. 1.2 Posicionamento do Produto Ramal Corporativo (Base) + Módulo Call Center Roadmap Futuro Voz HD (OPUS/G.711/G.722) Videochamada (H.264/VP8) Mensageria interna Push VoIP nativo Presença em tempo real Provisioning automático Tudo do plano base + Status de agente (pause/ACW) Motivo de pausa configurável Estatísticas de fila real-time Transferência supervisionada Integração discador preditivo Notificações RRPConnect* Relatórios de ramal (tarifador) Suporte técnico via chat * canal push separado do core SIP 1.3 Problema que Resolve Duplo login — portal web + softphone de terceiros sem sincronia Ausência de push VoIP — usuário precisa ter o app aberto para receber chamadas Sem status de agente integrado ao ramal (pause, ACW, presença) Impossibilidade de uso mobile real — usuários fixos no desktop Dependência de licença de terceiros sem controle de evolução do produto Videochamada e mensageria em ferramentas separadas, fora do ecossistema RRP 2. Arquitetura Técnica 4.1 Stack por Plataforma Componente Tecnologia Fonte Engine SIP/RTP/vídeo liblinphone (C++) via .aar / SPM / CMake gitlab.linphone.org/BC/public/linphone-sdk App Android Kotlin + Jetpack Compose — projeto novo Repositório RRP (criado do zero) App iOS Swift + SwiftUI — projeto novo Repositório RRP (criado do zero) App Desktop Qt 6.x + C++ — projeto novo Repositório RRP (criado do zero) Backend/API Laravel 12 + PostgreSQL Repositório RRP existente WebSocket eventos Laravel Reverb Integrado ao backend existente Push VoIP Android Firebase Cloud Messaging (FCM) Google Firebase Console Push VoIP iOS APNs VoIP via PushKit Apple Developer Program NAT Traversal coturn (STUN/TURN) Nova instância Oracle Cloud — obrigatório antes da Fase 1 Mensageria storage PostgreSQL via Laravel API (HTTP+Push) Repositório RRP existente Segurança credenciais Android Keystore / iOS Keychain Nativo — configurado via liblinphone 4.2 Fluxo de Chamada com Multi-Dispositivo — SIP CANCEL Nativo Etapa Ator Ação 1 Asterisk Recebe chamada SIP para o ramal do usuário 2 Laravel (ARI) Detecta evento; consulta agent_devices WHERE user_id=X AND active=true 3 Laravel Dispara push VoIP para TODOS os dispositivos ativos simultaneamente (FCM + APNs) 4 Todos os apps Acordam via FCM (Android) / PushKit (iOS) e registram ramal SIP via WSS 5 Asterisk SIP Forking — INVITE simultâneo para todos os registros do ramal 6 Primeiro app Usuário atende — responde com 200 OK 7 Asterisk Envia SIP CANCEL com cabeçalho RFC 3326 para todos os outros registros 8 Outros apps liblinphone recebe CANCEL → avisa ConnectionService/CallKit para encerrar tela 9 iOS/Android Interpretam &apos;cause=200&apos; nativamente — NÃO registram chamada perdida no histórico 10 RTP Flui direto entre Asterisk e o dispositivo que atendeu (SRTP/OPUS) ✅ Decisão Arquitetural — SIP CANCEL RFC 3326 (v3.1) A resolução de multi-dispositivo é feita 100% pelo protocolo SIP — sem orquestração pelo Reverb. Asterisk inclui no CANCEL: Reason: SIP; cause=200; text=&quot;Call completed elsewhere&quot; (RFC 3326) iOS (CallKit) e Android (ConnectionService) interpretam cause=200 nativamente: → Tela de chamada fecha silenciosamente → Chamada NÃO aparece como &apos;perdida&apos; no histórico do discador Vantagens sobre o Reverb: funciona offline, sem latência de WebSocket, sem código extra no app. Reverb (CallAnsweredElsewhere) mantido apenas como fallback para apps sem rede no momento do CANCEL. Limite: máximo 3 dispositivos simultâneos por usuário (max_contacts=3 no pjsip.conf). ⚙ Configuração Asterisk — Cabeçalho Reason no CANCEL No dialplan (extensions.conf) ou via ARI, adicionar antes do Dial(): same =&gt; n,Set(PJSIP_HEADER(add,Reason)=SIP\; cause=200\; text=&quot;Call completed elsewhere&quot;) Alternativa via endpoint no pjsip.conf: set_var=PJSIP_HEADER(add,Reason)=SIP\; cause=200\; text=&quot;Call completed elsewhere&quot; Verificar: o Asterisk deve incluir o header Reason no CANCEL enviado após 200 OK de outro fork. 4.3 Arquitetura de Mensageria — HTTP+Push ⚠ Decisão Arquitetural — SIP MESSAGE não é canal primário SIP MESSAGE via Asterisk é fire-and-forget. Se o destinatário estiver offline, a mensagem se perde. Canal primário: HTTP (POST /api/v1/messages) + Push notification via FCM/APNs. SIP MESSAGE: usado APENAS para &apos;digitando...&apos; em tempo real quando ambos os ramais estão online. Fluxo de envio de mensagem: App A envia POST /api/v1/messages (HTTP — confiável, auditável, suporta offline sender) Laravel persiste no PostgreSQL com timestamp server-side (fonte de verdade para ordenação) Laravel dispara push de mensagem nova via FCM/APNs para todos os dispositivos do destinatário App B, ao receber o push, executa GET /api/v1/messages/{conv_id} para buscar a mensagem Histórico server-side — funciona em novo dispositivo, reinstalação e troca de plataforma 4.4 Arquitetura de Videochamada liblinphone suporta H.264, H.265 e VP8 nativamente — sem biblioteca adicional Asterisk: habilitar allow=h264 e allow=vp8 no pjsip.conf (pré-requisito Fase 4) coturn obrigatório para vídeo em 4G/5G — mais sensível a NAT do que voz Bitrate adaptativo nativo do liblinphone — degrada automaticamente se banda insuficiente Fallback para voz: se banda insuficiente, liblinphone negocia áudio puro em &lt; 5 segundos 4.5 Provisioning e Segurança de Credenciais Usuário loga com credenciais RRP (JWT) — nunca vê campos de configuração SIP App chama POST /api/v1/softphone/provision Laravel retorna config SIP + credenciais TURN + feature flags do plano contratado App configura o Core liblinphone programaticamente OBRIGATÓRIO: credenciais SIP armazenadas no Android Keystore / iOS Keychain via liblinphone — nunca em SharedPreferences, UserDefaults, arquivo ou log App monta UI dinamicamente com base nas feature flags recebidas App registra token FCM/APNs via POST /api/v1/softphone/push-token com platform e device_id Heartbeat diário: PUT /api/v1/softphone/heartbeat para manter agent_devices.active=true 4.6 Isolamento do Core SIP para Notificações Externas 📋 Arquitetura — Notificações de Sistemas Externos (RRPConnect, tarifador etc.) O core SIP (liblinphone) é completamente isolado de qualquer sistema de notificação externo. Notificações externas (RRPConnect, tickets, relatórios) usam canal FCM/APNs INDEPENDENTE. Ao tocar notificação externa: app abre Fragment/View nativo dedicado ou WebView isolada. NUNCA misturar callbacks de push externo com o ciclo de vida do Core liblinphone. Motivo: crash em notificação externa não pode derrubar o stack de chamadas ativo. 4.7 Otimização de Bateria — Android 📋 Padrão da Indústria — REQUEST_IGNORE_BATTERY_OPTIMIZATIONS WhatsApp, Signal, Teams e todos os apps VoIP críticos solicitam essa permissão. Sem ela, fabricantes como Xiaomi, Huawei e Samsung matam o processo SIP em 20–30 min com tela desligada. A permissão deve ser solicitada no onboarding, logo após o primeiro login bem-sucedido. No iOS, o problema equivalente é tratado nativamente pelo PushKit + CallKit (sem permissão extra). Fluxo de onboarding da permissão de bateria (Android): Após login e provisioning concluídos, verificar se a permissão já foi concedida Se não concedida, exibir tela explicativa com linguagem simples: &apos;Para receber chamadas mesmo com a tela desligada, o RRP Softphone precisa ser excluído da otimização de bateria do Android&apos; Botão &apos;Configurar agora&apos; abre diretamente Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS Verificar novamente no boot do app — re-solicitar se o usuário tiver revogado Exibir indicador visual no status do agente se a permissão estiver ausente (aviso de conectividade) 5. Glossário Termo Definição ARI Asterisk REST Interface — API REST + WebSocket para controle programático do Asterisk APNs Apple Push Notification service — VoIP = modalidade especial via PushKit, obrigatória para CallKit CallKit Framework iOS que integra chamadas VoIP à UI nativa do sistema (tela de bloqueio, app Telefone) ConnectionService API Android equivalente ao CallKit — integração com tela de chamada nativa do sistema coturn Servidor open source STUN/TURN — obrigatório para NAT traversal em redes móveis 4G/5G FCM Firebase Cloud Messaging — push do Google para Android (canais VoIP e mensagens separados) Feature Flag Parâmetro booleano retornado no provisioning — controla funcionalidades disponíveis por plano Fire-and-forget Protocolo sem confirmação de entrega — razão pela qual SIP MESSAGE não é canal primário de mensageria GPL v3 Licença do liblinphone — permite uso em serviço gerenciado (SaaS) sem exigir abertura do código ICE Interactive Connectivity Establishment — protocolo para conectividade RTP atravessando NAT/firewall Keychain Armazenamento seguro de credenciais no iOS — equivalente ao Android Keystore Keystore Android Keystore System — armazenamento criptografado de credenciais ligado ao hardware liblinphone Biblioteca C++ core do SDK Belledonne — SIP, RTP, codecs, push, NAT, vídeo. Usada como .aar (Android), framework SPM (iOS) ou lib CMake (Desktop) MixMonitor Aplicação Asterisk que grava chamadas em .wav — usado no pipeline de QA de áudio automatizado MOS Mean Opinion Score — métrica objetiva de qualidade de voz (1–5). Meta: ≥ 4.0 Wi-Fi, ≥ 3.5 em 4G PushKit Framework iOS específico para push VoIP — acorda app em background profundo, obrigatório com CallKit RFC 3326 Reason Header for SIP — padrão que define o cabeçalho Reason no SIP CANCEL; cause=200 indica &apos;atendido em outro local&apos;, interpretado nativamente por iOS e Android REQUEST_IGNORE_BATTERY_OPTIMIZATIONS Permissão Android que exclui o app da otimização de bateria — obrigatória para manter registro SIP ativo com tela desligada em fabricantes como Xiaomi, Huawei e Samsung SIP Forking Capacidade do Asterisk de enviar INVITE simultâneo para múltiplos registros do mesmo ramal SIP MESSAGE Método SIP para texto em tempo real — usado SOMENTE para &apos;digitando...&apos; no RRP Softphone SRTP Secure Real-time Transport Protocol — RTP com criptografia AES, obrigatório para voz e vídeo WSS WebSocket Secure — transporte SIP sobre WebSocket com TLS, obrigatório para apps móveis atrás de NAT
